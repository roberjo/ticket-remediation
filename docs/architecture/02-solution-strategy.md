# 2. Solution Strategy

The decisions below are the load-bearing ones — each is written as decision / context /
consequence so a reader can judge whether the reasoning still holds before changing it.

## ADR-1: Connectors are `typing.Protocol`s, not base classes

**Decision.** Every external system (ServiceNow, Jira, GitHub, LLM provider, Notifier) is defined
as a structural `Protocol` in `connectors/<name>/base.py`, with one or more concrete
implementations alongside it.

**Context.** Quality goal #4 (testability) requires exercising pipeline orchestration logic
without hitting real services in the default test run.

**Consequences.** Tests build hand-written fake classes that satisfy a Protocol with zero
inheritance from the real implementation — see `tests/unit/ingest/test_ingest_pipeline.py` and
`tests/unit/remediate/test_remediate_pipeline.py`. Adding a second implementation (e.g. the
Gemini LLM provider alongside Anthropic) requires no change to the Protocol or to any code that
already depends on it — `mypy` verifies structural compatibility statically.

## ADR-2: Both pipelines are polling CLIs, not webhook receivers

**Decision.** `ingest` and `remediate` are `typer` CLIs with a `run` command, meant to be invoked
by cron. There is no inbound HTTP server in v1.

**Context.** Quality goal #2 (zero-cost developability) — a webhook receiver needs a publicly
reachable endpoint, TLS, and signature verification before it's usable, none of which is free or
quick to stand up for local development.

**Consequences.** Both `IngestPipeline` and `RemediatePipeline` are plain classes with a `.run()`
method and no knowledge of how they were invoked. The CLI (`ingest/__main__.py`,
`remediate/__main__.py`) is a thin adapter — a future webhook receiver (e.g. a small FastAPI app)
could call `pipeline.run()` directly with no pipeline-level changes. The trade-off is latency:
findings and issues are only picked up on the next scheduled poll, not instantly.

## ADR-3: State/idempotency lives in one local SQLite file

**Decision.** A two-table SQLite database (`data/state.db`) tracks SNOW-ticket → Jira-key links
and Jira-key → remediation-run status, with plain `sqlite3` (no ORM).

**Context.** Quality goal #1 (safety/idempotency) needs durable state to guarantee "never create
this twice", and quality goal #2 (zero-cost) rules out a managed database service.

**Consequences.** Idempotency is a lookup, not a distributed-systems problem. The trade-off:
single-writer, single-machine only — this does not scale to multiple concurrent pipeline
instances. That's an explicit non-goal for v1 (see [Risks](08-cross-cutting-and-risks.md)).

## ADR-4: The LLM returns full file contents, not diffs

**Decision.** `RemediationResponse.edits` carries the complete new content of each changed file,
not a unified diff.

**Context.** Unified diffs generated by an LLM frequently fail to apply because of context-line
drift (the model's mental model of line numbers/context doesn't always match the real file
byte-for-byte).

**Consequences.** Applying a `FileEdit` is a deterministic `write_text()`/`unlink()` — no patch
library, no fuzzy-matching, no partial-apply failure mode. The cost is more tokens per response,
which is acceptable because repo context is already deliberately narrow (ADR-5).

## ADR-5: The LLM pulls its own context via a bounded `read_file` tool

**Decision.** The provider is handed the repo's file tree plus a `file_reader` callback, not the
full repo contents. It requests specific files via tool-use, capped at `MAX_FILE_READS` reads and
`MAX_FILE_BYTES` per read (`connectors/llm/limits.py`), and any path that escapes the repo
working directory is rejected before the read happens.

**Context.** Dumping an entire repository into the prompt doesn't scale token-wise and doesn't
match how a human engineer actually investigates a ticket (targeted reads, not a full dump). The
path-escape guard exists because file paths in this loop originate from a model response, which
is treated as untrusted input.

**Consequences.** The same mechanism works unmodified for a React frontend, an Express backend,
or Terraform HCL — nothing in `context_builder.py` or the provider code is language-aware. This
is what let the system's scope grow from "React app vulnerabilities" to "React app +
infrastructure-as-code vulnerabilities" as a **config and content change**, not an architecture
change (see [Building Block View](03-building-blocks.md) and
[ADR-8](#adr-8-vulnerability-domain-is-config-driven-not-hardcoded)).

## ADR-6: LLM provider is pluggable, selected by one config value

**Decision.** `connectors/llm/factory.py::get_llm_provider(settings)` switches on
`LLM_PROVIDER` (`anthropic` | `gemini`) and returns the matching implementation of the
`LLMProvider` Protocol.

**Context.** Quality goal #2 (zero-cost) — Anthropic's API has a real per-call cost; Gemini's
free tier does not. Neither should be hardwired.

**Consequences.** The two implementations don't share a wire protocol — Anthropic uses
`messages.create` with `tool_use` content blocks; Gemini uses the newer stateful `interactions`
API with `previous_interaction_id`-based continuation. Each provider owns its own tool-declaration
shape and read-loop; only the `LLMProvider` Protocol and the shared `limits.py` constants are
common. Adding a third provider means one new file plus one `elif` branch in the factory.

## ADR-7: Mapping and routing rules are YAML, validated by pydantic, not hardcoded

**Decision.** `config/ingest_mapping.yaml` (SNOW table → Jira fields) and
`config/repo_routing.yaml` (Jira project/component → GitHub repo) are lists of rules, loaded and
validated into pydantic models (`config/mapping.py`).

**Context.** Quality goal #3 (extensibility) — broadening scope (a new source table, a new
target repo) should not require a code change or a new deploy.

**Consequences.** v1 populates exactly one rule in each file; the schema already supports many.
Extending `repo_routing.yaml`'s `components` list from `[frontend, backend-api]` to
`[frontend, backend-api, infra-config]` — the actual change that added Terraform remediation
support — was a two-line YAML edit, not a code change.

## ADR-8: Vulnerability domain is config-driven, not hardcoded

**Decision.** The mock ServiceNow server's vulnerability catalog
(`mock_servers/servicenow_mock/vuln_catalog.py`) is a flat, data-only list of `CatalogEntry`
records, each independently tagged with a `component` and a `demo_relevant` flag. Nothing in the
ingest or remediate pipeline branches on vulnerability type.

**Context.** The system needed to grow from "web-app vulnerabilities against a React/Express
app" to "web-app vulnerabilities **and** cloud-infrastructure misconfigurations against
accompanying Terraform" without becoming two systems.

**Consequences.** Because `affected_component` flows unmodified from the SNOW ticket through
Jira `components` to `repo_routing.yaml` matching (ADR-7), adding the `infra-config` domain was:
5 new catalog entries, 5 new `.tf` files in the demo repo, and one routing-config line — see
[ADR-5](#adr-5-the-llm-pulls-its-own-context-via-a-bounded-read_file-tool) for why the
remediation step itself needed zero changes.

## ADR-9: `uv` for packaging; no Poetry, no bare pip

**Decision.** `uv` manages the virtualenv, dependency resolution, and lockfile
(`pyproject.toml` + `uv.lock`).

**Context.** Single, fast, actively maintained tool that needs no separate installation step
beyond itself; no strong reason found to prefer Poetry for a greenfield project.

**Consequences.** `uv sync`, `uv run`, `uv add` are the only commands contributors need to learn.

## ADR-10: GitHub PR review is the only approval gate

**Decision.** There is no human-approval step between the LLM producing a fix and a PR being
opened; the PR itself, and normal code review, is the checkpoint.

**Context.** This was an explicit product decision (not a technical constraint) made early in
scoping this project: adding a bespoke approval-workflow layer would duplicate what GitHub PR
review already does well.

**Consequences.** The system's blast radius if the LLM gets something wrong is bounded by
"opens a PR nobody has to merge" — never a direct push to a protected branch. This is why
[Cross-Cutting Concerns](08-cross-cutting-and-risks.md) treats PR review, not the LLM's output,
as the actual security boundary.
